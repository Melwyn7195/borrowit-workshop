The task definition describes *what* to run; the service describes *how many* and
*where*, and keeps that true over time.

#### The task definition

```typescript
const taskDefinition = new ecs.FargateTaskDefinition(this, 'TaskDefinition', {
  cpu: 256,
  memoryLimitMiB: 512,
});
```

0.25 vCPU and 512 MiB — the smallest valid Fargate combination, about **$9/month**
running continuously. Fargate only accepts specific CPU/memory pairs; 256 CPU units
allows 512, 1024 or 2048 MiB and nothing else.

#### Configuration in, secrets separately

```typescript
environment: {
  PORT: '3456',
  NODE_ENV: 'production',
  AWS_REGION: this.region,
  AWS_S3_BUCKET: props.uploadsBucket.bucketName,
  ASSET_BASE_URL: props.distributionUrl,
  FRONTEND_URL: props.distributionUrl,
},
secrets: {
  DB_HOST: ecs.Secret.fromSecretsManager(dbSecret, 'host'),
  DB_PORT: ecs.Secret.fromSecretsManager(dbSecret, 'port'),
  DB_USER: ecs.Secret.fromSecretsManager(dbSecret, 'username'),
  DB_PASSWORD: ecs.Secret.fromSecretsManager(dbSecret, 'password'),
  DB_NAME: ecs.Secret.fromSecretsManager(dbSecret, 'dbname'),
  JWT_SECRET: ecs.Secret.fromSecretsManager(jwtSecret, 'jwtSecret'),
},
```

Non-sensitive configuration goes in `environment`; anything secret goes in
`secrets`, which stores only an ARN. See
[3.3.4](../../3.3-Architecture/3.3.4-delivery-and-secrets/) for why that
distinction matters.

Three values are worth noting:

+ **`AWS_REGION` must be set explicitly.** Unlike EC2, a Fargate task does not
  give the SDK a region automatically, and the upload path reads it directly.
+ **`ASSET_BASE_URL` and `FRONTEND_URL` come from the frontend stack.** This is
  the import that makes `BorrowitApp` depend on `BorrowitFrontend` — and the
  reason nothing may depend on `BorrowitApp` in return.
+ **`JWT_SECRET` is the one secret this stack generates itself.** The database
  password comes from RDS; this one has no service to generate it, so AppStack
  creates it.

#### The second secret

```typescript
const jwtSecret = new secretsmanager.Secret(this, 'JwtSecret', {
  description: 'BorrowIt API token signing key',
  generateSecretString: {
    secretStringTemplate: JSON.stringify({}),
    generateStringKey: 'jwtSecret',
    passwordLength: 64,
    excludePunctuation: true,
  },
  removalPolicy: cdk.RemovalPolicy.DESTROY,
});
```

This signs the session cookie. Without it every login returns **500** with
`secretOrPrivateKey must have a value` — `jwt.sign` refuses an undefined key
rather than falling back to anything.

It is generated by CloudFormation for the same reason the database password is
generated by RDS: a value written into `cdk.json` or a `.env` is a value in git
history. `excludePunctuation` keeps it to characters that never need escaping
anywhere in the chain, since it is read back as an environment variable.

{{% notice note %}}
Destroying and redeploying `BorrowitApp` regenerates this secret, which
invalidates every token already issued. In practice that means everyone logs in
again — worth knowing before you tear the stack down mid-demonstration.
{{% /notice %}}

`JWT_REFRESH_SECRET` is deliberately **not** set: `userController.js` already
falls back to `JWT_SECRET` for refresh tokens, and a second secret is another
$0.40/month. Splitting them is a hardening step, not a fix.

#### The container health check

```typescript
healthCheck: {
  command: ['CMD-SHELL', "node -e \"...http://127.0.0.1:3456/health/live...\""],
  interval: cdk.Duration.seconds(30),
  timeout: cdk.Duration.seconds(5),
  retries: 3,
  startPeriod: cdk.Duration.seconds(15),
},
```

This is the **liveness** check: is the Node process alive? It deliberately does
**not** touch the database. The readiness check that does is on the load balancer —
see [3.6.3](../3.6.3-load-balancer/).

{{% notice note %}}
ECS **ignores** the `HEALTHCHECK` instruction in the Dockerfile. It must be
restated in the task definition. The Dockerfile version is kept only so that a
local `docker run` behaves the same way.
{{% /notice %}}

#### The service

```typescript
const service = new ecs.FargateService(this, 'Service', {
  cluster,
  taskDefinition,
  desiredCount,
  assignPublicIp: true,
  vpcSubnets: { subnetType: ec2.SubnetType.PUBLIC },
  securityGroups: [props.serviceSecurityGroup],
  circuitBreaker: { rollback: true },
  enableExecuteCommand: true,
  minHealthyPercent: 50,
  maxHealthyPercent: 200,
});
```

| Setting | Effect |
|---|---|
| `assignPublicIp` + `PUBLIC` subnets | Outbound access without a NAT Gateway — [3.3.3](../../3.3-Architecture/3.3.3-networking/) |
| `securityGroups` | Inbound restricted to the load balancer on 3456 |
| `circuitBreaker: { rollback: true }` | A deployment failing health checks rolls itself back |
| `enableExecuteCommand` | Opens a shell inside a running task — [3.6.4](../3.6.4-database-init/), [3.8.4](../../3.8-Observability/3.8.4-debugging/) |
| `minHealthyPercent: 50` | At one task, ECS stops the old before starting the new |

#### Deployment safety without paying for it

`minHealthyPercent: 50` with `desiredCount: 1` permits ECS to drop to zero healthy
tasks during a deployment — so a deploy never runs two tasks simultaneously and
never costs double.

The tradeoff is **a few seconds of downtime per deployment**. At `desiredCount: 2`
you would set `minHealthyPercent: 100` for zero-downtime rolling deploys and pay
for the second task permanently.

The circuit breaker is the safety net that makes this acceptable: if the new task
never passes its health checks, ECS stops the rollout and restores the previous
task definition automatically, rather than leaving the service down.

#### Deploy

```powershell
cd ..\infra
npx cdk deploy BorrowitApp -c imageTag=v1 -c alarmEmail=you@example.com
```

Takes about **5 minutes**.

`-c alarmEmail` is optional here and covered properly in
[3.8.3](../../3.8-Observability/3.8.3-alarms/) — passing it now saves a second
five-minute deploy later. `-c imageTag` is not optional: it defaults to `latest`,
and 3.6.1 pushed `v1`.

{{% notice note %}}
This deploy will pull `BorrowitFrontend` along with it if you have not deployed
that stack yet, because the task definition reads the uploads bucket name and
distribution URL from it. Once it finishes, run `npm run wire` so CloudFront
learns the new load balancer's hostname — [3.7](../../3.7-Delivery/).
{{% /notice %}}
