Congratulations on completing this workshop.

#### What was built

A complete system on AWS, defined entirely in code, with every service choice
justified against a named alternative:

+ **Compute** — ECS on Fargate rather than Lambda, because the workload is a
  long-lived process with a connection pool, and RDS Proxy would have erased
  Lambda's price advantage.
+ **Database** — RDS PostgreSQL rather than Aurora Serverless v2 or DynamoDB,
  because the schema already exists and a fixed cost beats a variable one on a
  fixed credit balance.
+ **Networking** — public subnets with no NAT Gateway, because a NAT costs more
  than the entire compute budget, with isolation moved into a chain of security
  groups and then demonstrated.
+ **Delivery** — S3 behind CloudFront with Origin Access Control, so the buckets
  are never public, and the API routed through the **same distribution** so it is
  same-origin with the page that calls it — which is what makes an HTTPS frontend
  and an HTTP-only load balancer work together at all.
+ **Secrets** — Secrets Manager, holding two values neither of which a human has
  seen: the database password generated by RDS, and the JWT signing key generated
  by CloudFormation.
+ **Observability** — CloudWatch logs, metrics, a dashboard and seven alarms,
  including one where missing data is deliberately treated as a breach.

#### What to tear down, and what not to

The four-stack split exists to make this decision simple.

| Stack | Cost/month | Recommendation |
|---|---|---|
| `BorrowitApp` | ~$35 | Destroy for a multi-week gap |
| `BorrowitData` | ~$16 | **Keep** — destroying it drops the data |
| `BorrowitFrontend` | ~$1 | Keep |
| `BorrowitFoundation` | ~$0 | Keep |

Destroy only the expensive layer:

```powershell
cd infra
npm run down       # cdk destroy BorrowitApp - about 2 minutes
```

Data and pushed images survive, because RDS lives in `BorrowitData` and the ECR
repository in `BorrowitFoundation` — both deliberate placements made in
[3.4](../3.4-Network/) and [3.5](../3.5-Data/). Restore with:

```powershell
npx cdk deploy --exclusively BorrowitApp -c imageTag=v1
npm run wire
```

`npm run up` chains exactly those two commands — but it does **not** pass
`-c imageTag`, so it deploys the default tag `latest`. If you followed
[3.6.1](../3.6-Compute/3.6.1-image-and-registry/) and pushed `v1` rather than
`latest`, the restored task will fail to start with `CannotPullContainerError`.
Either pass the tag explicitly as above, or push a `latest` tag as well.

{{% notice note %}}
`npm run wire` is needed here because destroying `BorrowitApp` destroys the load
balancer, and the replacement gets a **new DNS name**. Without re-wiring,
CloudFront keeps routing `/api/*` at a hostname that no longer resolves — and
because the SPA fallback is scoped to the default behaviour, those calls fail
rather than quietly returning HTML. Restoring the stack is exactly the case
[3.7](../3.7-Delivery/) warns about.
{{% /notice %}}

{{% notice warning %}}
Do **not** run `cdk destroy --all` unless you are finished with the project
entirely. `BorrowitData` uses `removalPolicy: DESTROY`, so destroying it deletes the
database **and** its automated backups. Rebuilding means re-running the schema and
seed from [3.6.4](../3.6-Compute/3.6.4-database-init/).
{{% /notice %}}

#### Full teardown

Only when the project is genuinely over:

```powershell
npx cdk destroy BorrowitApp
npx cdk destroy BorrowitFrontend
npx cdk destroy BorrowitData
npx cdk destroy BorrowitFoundation
```

**Order matters.** `BorrowitApp` must go first — it is the stack that imports
values from the other three, and CloudFormation will refuse to delete a stack whose
outputs are still being imported. This is the one-way dependency from
[3.1](../3.1-Overview/) showing up one last time.

The `CDKToolkit` bootstrap stack is left in place. It costs essentially nothing and
is needed again on the next deployment.

#### Confirm nothing is still billing

```powershell
aws elbv2 describe-load-balancers --region ap-southeast-1 --query "LoadBalancers[].LoadBalancerName"
aws rds describe-db-instances --region ap-southeast-1 --query "DBInstances[].DBInstanceIdentifier"
aws ecs list-clusters --region ap-southeast-1
aws ec2 describe-addresses --region ap-southeast-1 --query "Addresses[].PublicIp"
```

The last one matters: an unassociated Elastic IP still bills, and is easy to leave
behind.

Then check the credit balance:

```powershell
aws freetier get-account-plan-state
```

#### Known limitations

Naming what was left undone is more useful than implying it was all finished:

| Limitation | Impact | Remedy |
|---|---|---|
| **The ALB is reachable directly over HTTP** | Anyone who knows the hostname can bypass the edge and call the API unencrypted | Restrict the ALB security group to the CloudFront `origin-facing` prefix list ($0), or a domain + ACM certificate ([3.7](../3.7-Delivery/)) |
| **CORS is set to `origin: true`** | The API reflects any origin with credentials allowed. Moot for the browser path now that it is same-origin, but it does widen the direct-to-ALB exposure above | Pin to the CloudFront domain |
| **No CI/CD** | Deployments run from a workstation | GitHub Actions to build, push and `cdk deploy` |
| **Single AZ by default** | Database is a single point of failure | Multi-AZ, at double the cost |
| **No automated tests** | The deployment circuit breaker is the only safety net | Add a test suite before adding CI/CD |
| **Secrets are not rotated** | A leaked database password stays valid indefinitely | Secrets Manager rotation via Lambda — not enabled here on scope and cost grounds |
