Three smaller decisions, each with a defensible alternative.

## Static delivery

#### The candidates

| Option | Monthly cost | Notes |
|---|---|---|
| **S3 + CloudFront** | ~$0.50 | Global edge caching; buckets stay private |
| **AWS Amplify Hosting** | ~$0.15 + build minutes | Simplest; couples hosting to a Git workflow |
| **Serve from the ALB** | $0 extra | Adds load to the API; no edge caching |

#### The decision

**Amazon S3 with Amazon CloudFront.** The application is a compiled single-page
bundle plus user-uploaded images — static objects that benefit from edge caching
close to users in Southeast Asia.

Serving them from the ALB was rejected because it puts static asset traffic
through the Fargate task, consuming the compute you are paying for and losing
caching entirely.

Amplify Hosting was the closer call: cheaper, and it handles builds. It was
rejected because it abstracts away the S3 and CloudFront configuration this
workshop exists to demonstrate, and because it assumes a Git-connected build
pipeline that does not exist here.

#### Keeping the buckets private

Both buckets use `BlockPublicAccess.BLOCK_ALL`. CloudFront reaches them through
**Origin Access Control**, which signs its requests to S3 with SigV4; the bucket
policy trusts only that distribution.

The common alternative — S3 static website hosting with a public-read bucket
policy — makes the bucket readable by anyone who guesses its name. OAC gives
public readability *through CloudFront* without public readability *of the bucket*.

`PRICE_CLASS_200` is used: it includes Southeast Asia and omits the most expensive
edge locations in South America and Oceania.

#### One distribution, three origins

The same distribution also fronts the **API**, on `/api/*`, `/health` and
`/api-docs*`. That was not part of the original delivery decision — it was forced
later by two constraints that only appear once the frontend is actually deployed:
an HTTPS page cannot call the HTTP-only load balancer, and a `sameSite=strict`
session cookie does not survive a cross-site API host.

It is worth noting here because it changes what CloudFront is *for* in this
architecture: not just a cache, but the thing that makes the API same-origin and
removes the need for CORS. [3.7](../../4.7-Delivery/) builds it.

## Secret storage

#### The candidates

| Option | Cost | RDS integration | Rotation |
|---|---|---|---|
| **AWS Secrets Manager** | $0.40/secret/month | **Native** — RDS generates and stores | Built in |
| **SSM Parameter Store** (standard) | Free | Manual | Manual |
| **Environment variables** | Free | None | None |

#### The decision

**AWS Secrets Manager**, chosen for one specific reason: `rds.Credentials.fromGeneratedSecret()`
means the password is generated by RDS and written straight into Secrets Manager.
**No human ever sees it, and it never exists outside AWS.**

Parameter Store is free and would work, but it requires generating the password
yourself and putting it somewhere to pass it in — which is exactly the failure
mode being designed out.

$0.40/month is a reasonable price for removing an entire class of credential leak.

#### Two secrets, generated two different ways

| Secret | Generated by | Lives in | Regenerated when |
|---|---|---|---|
| Database credentials | **RDS**, via `fromGeneratedSecret()` | `BorrowitData` | `BorrowitData` is recreated |
| JWT signing key | **CloudFormation**, via `generateSecretString` | `BorrowitApp` | `BorrowitApp` is recreated |

The API signs its session cookies with a key that has no service to generate it
the way RDS generates a database password — so `BorrowitApp` creates one itself
([3.6.2](../../4.6-Compute/4.6.2-task-and-service/)). The principle is the same
either way: **the value is generated inside AWS and no human ever sees it.** The
alternative — inventing a signing key and pasting it into `cdk.json` — puts it in
git history permanently.

The placement follows the lifecycle. The database key belongs with the database;
the signing key belongs with the API, and losing it when `BorrowitApp` is
destroyed costs nothing worse than everyone logging in again.

#### How the value reaches the container

The distinction between `environment` and `secrets` in an ECS task definition is
the whole point:

+ `environment` values are stored **literally** in the task definition. Anyone with
  `ecs:DescribeTaskDefinition` can read them.
+ `secrets` values store only the **ARN**. ECS resolves them at task start using
  the execution role, so the value never appears in the task definition, the
  console, or the CloudFormation template.

```typescript
secrets: {
  DB_HOST: ecs.Secret.fromSecretsManager(dbSecret, 'host'),
  DB_PASSWORD: ecs.Secret.fromSecretsManager(dbSecret, 'password'),
  // ...
},
```

## Container registry

**Amazon ECR**, over Docker Hub or GitHub Container Registry, for three reasons:

+ **IAM-native authentication** — no registry credentials to store anywhere.
+ **Same-region pulls** — the task pulls from `ap-southeast-1`, so image pull is
  fast and incurs no cross-region transfer.
+ **`imageScanOnPush`** — free basic vulnerability scanning on every push.

The repository lives in `BorrowitFoundation` rather than `BorrowitApp`, so that
destroying the application layer does not discard images already pushed. A
lifecycle rule caps storage at ten images.

{{% notice note %}}
**Combined cost of everything on this page:** roughly **$1.50/month** — S3 storage
and requests, CloudFront transfer at low volume, **two** Secrets Manager secrets
at $0.40 each, and ECR storage for ten small images.
